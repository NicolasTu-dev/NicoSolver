# Spanish Localization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add Spanish as a third UI language (alongside English/Chinese), fix a latent combo-box translation bug that would otherwise break language/theme persistence once translations are active, and fix a real regression introduced by phases 1-3 of this redesign where several new UI strings were written in Spanish as their `tr()` source text — meaning English-locale users currently see un-translated Spanish text for the wizard, legend, and results-screen toggle.

**Architecture:** This app already has a complete Qt Linguist i18n pipeline (`.ts` source → `lupdate` extraction → hand-translation → `lrelease` compilation → `.qm` → bundled via `translations.qrc` → loaded via `QTranslator` in `main.cpp` based on a `QSettings` key). This plan extends that exact pipeline with a third locale; it does not introduce any new i18n mechanism.

**Tech Stack:** Qt Linguist tools (`lupdate.exe`, `lrelease.exe`, confirmed present at `D:\QT\6.11.2\mingw_64\bin\`), Qt `.ts`/`.qm` translation files, C++/Qt.

### Task 3: Regenerate translation source files and fix the Spanish-as-source-text regression

**Files:**
- Modify: `lang_en.ts`, `lang_cn.ts` (regenerated in place by `lupdate`, then hand-edited)
- Create: `lang_es.ts` (via `lupdate`)

**Interfaces:**
- Consumes: `TexasSolverGui.pro`'s `TRANSLATIONS` list (now includes `lang_es.ts` from Task 2).
- Produces: `.ts` files containing every current `tr()`/`.ui`-string, ready for `lrelease` in Task 4.

**Background (why this task exists, not just "add Spanish"):** Codebase research confirmed several strings added during phases 1-3 of this redesign — the wizard navigation labels/step names, the results-screen legend labels, and the "Modo avanzado (mostrar EV)" checkbox — were written with **Spanish text as their literal `tr()` source string** (e.g. `tr("Siguiente →")`, `tr("Cargar configuración guardada")`). Since this project's established convention is English-as-source (that's what `lang_en.ts` already contains for every pre-existing string), this means **English-locale users currently see un-translated Spanish text** for those specific new UI elements — a real regression, not a hypothetical one. This task fixes it by giving those specific strings a proper English `<translation>` entry, while Spanish-locale users need no new translation for them at all (the source already IS the correct Spanish text).

- [ ] **Step 1: Run lupdate**

Run the `lupdate` command from Global Constraints. This scans all source/`.ui` files listed in `TexasSolverGui.pro` and updates `lang_en.ts`, `lang_cn.ts` in place (new `<message>` entries added for strings not yet captured, marked `type="unfinished"`), and creates `lang_es.ts` fresh (every message unfinished, since nothing's been translated into it yet).

- [ ] **Step 2: Identify the Spanish-source strings needing an English translation**

In the freshly-updated `lang_en.ts`, find the newly-added `<message>` entries whose `<source>` text is itself Spanish (not English) — per prior research, this includes at minimum: `Rangos`, `Board` (already English, skip), `Bet Sizings` (already English, skip), `Parámetros del árbol`, `Opciones del Solver`, `Confirmar y resolver`, `Paso %1 de 6: %2`, `Listo`, `Siguiente →`, `← Atrás`, `Cargar configuración guardada`, `Modo avanzado (mostrar EV)`, `Theme`/`Dark`/`Light`/`Español` (these last four are already English, skip). For each Spanish-source entry, fill in its `<translation>` element with the correct natural English equivalent (e.g. `Parámetros del árbol` → `Tree Parameters`, `Confirmar y resolver` → `Confirm and Solve`, `Cargar configuración guardada` → `Load saved configuration`, `Modo avanzado (mostrar EV)` → `Advanced mode (show EV)`, `Listo` → `Done`, `← Atrás` → `← Back`, `Siguiente →` → `Next →`), and remove the `type="unfinished"` attribute from that `<translation>` tag (Qt only applies a translation once it's marked finished — leaving `type="unfinished"` means Qt still falls back to displaying the source text).

- [ ] **Step 3: Translate lang_es.ts**

For every `<message>` in `lang_es.ts` whose `<source>` is already Spanish (the same list identified in Step 2, plus `Theme`→`Tema`, `Dark`→`Oscuro`, `Light`→`Claro`, `Español`→`Español`), set `<translation>` to the identical source text (trivial, since source already is Spanish) and remove `type="unfinished"`. For every OTHER message (the ~200 pre-existing English-source strings covering the original app's rangeselector/boardselector/mainwindow/strategyexplorer/settingeditor UI, poker terminology, error messages, etc. — read the full file to see the actual list), write a natural, accurate Spanish translation appropriate for a poker-solver desktop application (use standard Spanish poker terminology: e.g. "range" → "rango", "board" → "board" or "tablero" — check `resources/` or existing `lang_cn.ts` context comments if any hint at preferred terminology, otherwise use standard conventions), and remove `type="unfinished"` from each. Handle the `%1`/`%2` placeholder entries (identified in prior research: a board-format error, two range-format errors, and the wizard's "Paso %1 de 6: %2") by preserving the placeholders in the same relative position/count in the Spanish text.

This is a substantial content-writing task (~200+ short strings). Prioritize accuracy and natural phrasing over speed; this is not a task to rush or leave partially `unfinished` — every message should end up with a real, finished translation, since a mix of translated/untranslated text reading inconsistently is worse than not offering Spanish at all.

- [ ] **Step 4: Verify no `unfinished` markers remain**

Run: `grep -c 'type="unfinished"' lang_es.ts` and `grep -c 'type="unfinished"' lang_en.ts`. Expected: `lang_es.ts` returns 0 (every message translated). `lang_en.ts` may still have some pre-existing unfinished entries if any existed before this branch (that's not this task's responsibility to fix) — but confirm specifically that none of the ~11 Spanish-source strings from Step 2 remain unfinished (spot-check by grepping for a few of them, e.g. `grep -A2 "Cargar configuración guardada" lang_en.ts` should show a finished `<translation>Load saved configuration</translation>`).

- [ ] **Step 5: Commit**

```bash

Task 3's translation-writing step is necessarily a large content-generation task rather than pre-written text (writing out 200+ Spanish translations in the plan document itself would bloat it enormously and the plan can't know the exact final English source strings until `lupdate` actually runs) — this mirrors the same "read the real file, then act" pattern used successfully in every prior plan in this project for cases where hand-transcribing exact content in advance isn't feasible, and is scoped with clear acceptance criteria (Task 3 Step 4's `unfinished` count check) rather than left vague.
